# Как участвовать

Спасибо за интерес к проекту. Этот документ описывает, как подготовить изменение, чтобы его приняли в `main`. Правила для автоматических помощников те же и лежат в [AGENTS.md](AGENTS.md); при расхождении AGENTS.md главнее.

Полезные документы: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) (устройство скриптов), [docs/README.md](docs/README.md) (оглавление руководств), [SECURITY.md](SECURITY.md) (уязвимости), [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md) (правила общения).

## Перед началом

- Откройте issue по форме «Ошибка» или «Предложение» и дождитесь ответа. Так изменение не разойдется с планом в `docs/plan.md` и не повторит чужую работу.
- Уязвимости не описывайте в issue: только закрыто, как сказано в [SECURITY.md](SECURITY.md).
- Небольшие правки документации (опечатка, битая ссылка) можно присылать сразу PR.

## Окружение

- bash 5 (проверки описаны для bash 5.3).
- shellcheck 0.11.0: версия закреплена в `.github/shellcheck.txt`, CI ставит именно ее. Другая версия может дать другие предупреждения.
- git и coreutils.

## Правило безопасности

Скрипты меняют ядро, пользователей, sudoers, SSH, firewall и sysctl. На рабочей станции не запускайте их ни от root, ни через sudo. Запуск от root — только на одноразовой Debian 12/13: виртуальная машина, контейнер с systemd или снимок VPS, который не жалко потерять. `upgrade-to-debian13.sh` проверяйте на одноразовой Debian 11/12.

`bash <скрипт> --help` у всех пяти скриптов работает без root и ничего не меняет. Остальные тесты из `tests/` тоже не требуют root и не трогают систему.

## Устройство: встроенные копии lib/

Каждый `optimize_*.sh` обязан работать одним файлом, потому что его запускают через `bash <(curl ...)`. Функции из `lib/*.sh` подключаются, только если каталог `lib` лежит рядом со скриптом; иначе работают встроенные копии (группами под `if ! declare -F`).

Меняете функцию в `lib/` — меняйте ее копии в каждом `optimize_*.sh`, где она есть. Копии сверяет с `lib/` тест `tests/test_embedded_copies.sh`; он падает при любом расхождении. `upgrade-to-debian13.sh` от `lib/` не зависит.

## Стиль

Следуйте стилю файла, который правите:

| Файл | Shebang и режим | Вывод |
|---|---|---|
| `optimize_vps.sh`, `optimize_mini_pc.sh`, `optimize_wsl2.sh` | `#!/bin/bash`, `set -e` или `set -Eeuo pipefail` | `log`, `warn`, `error`, `info`, `progress`, `section` |
| `optimize_amnezia_host.sh` | `#!/usr/bin/env bash`, `set -euo pipefail` | единые помощники чистого вывода |
| `upgrade-to-debian13.sh` | `#!/usr/bin/env bash`, `set -euo pipefail` | `log`, `warn`, `err` |

- В новых скриптах — `#!/usr/bin/env bash` и `set -euo pipefail`.
- Отступ 4 пробела внутри функций и условий; настройки редактора лежат в `.editorconfig`.
- Имена функций строчными буквами с подчеркиванием (`wait_for_dpkg_lock`), глобальные переменные и константы — прописными (`LOG_FILE`, `SCRIPT_VERSION`).
- Имена файлов строчными буквами через подчеркивание, по окружению: `optimize_wsl2.sh`.
- Сообщения пользователю — короткие и операционные; существующие помощники вывода не заменяйте.
- Без пробелов в конце строк во всех текстовых файлах: их, как и ссылки и якоря Markdown и версии скриптов в таблице README, проверяют тесты `tests/test_repository_hygiene.sh` и `tests/test_docs_links.sh`.

## Тесты

Тесты лежат в `tests/`, каждый — отдельный Bash-файл, который завершается кодом 0 при успехе и ненулевым кодом с сообщением `FAIL: ...` при ошибке. Новое поведение сопровождайте тестом или дополнением существующего.

Временные файлы в тестах — только через `mktemp` с удалением в `trap`. Фиксированный путь в общем `/tmp` у раннера под другим пользователем не записывается (`fs.protected_regular`), и тест проходит ложно.

## Документация

Документация — часть изменения. Если меняется поведение, поддерживаемые версии, требования или ограничения безопасности, обновите в том же PR:

- `README.md` (таблица возможностей и версий);
- руководство в `docs/` для затронутого окружения; `docs/README_UPGRADE.md` — при изменении обновления или поддерживаемых версий Debian;
- `CHANGELOG.md` — запись об изменении.

Команды в документах должны копироваться и работать как есть; версии в разных файлах — совпадать.

## Проверка перед PR

Быстрый сигнал (около секунды): `bash -n <файл>` и `bash tests/<затронутый тест>.sh`. Учтите: `bash -n a.sh b.sh` проверяет только `a.sh`, остальные файлы становятся аргументами.

Полная проверка — из корня репозитория и не от root (иначе `tests/test_root_privileges_check.sh` пропускается), около 10 секунд:

```bash
bash -c 'for f in *.sh lib/*.sh tests/*.sh; do bash -n "$f" || exit 1; done'
shellcheck -- *.sh lib/*.sh tests/*.sh
bash -c 'for t in tests/*.sh; do bash "$t" || exit 1; done'
git diff --check origin/main
```

Измененный путь кода прогоните на одноразовой Debian нужного окружения (VPS, мини-ПК, WSL2 или лаборатория обновления) и опишите результат в PR. Если поведение зависит от Debian 13, Docker, CUDA, пакетов ядра, SSH или оборудования, запишите, что именно проверено и где.

## Коммиты

Conventional Commits с именем затронутого скрипта в теме, повелительное наклонение, коротко:

```
feat: add swap tuning to optimize_mini_pc.sh
fix: remove redundant fi in upgrade-to-debian13.sh
docs: update CUDA install notes in README_WSL2.md
```

Префиксы: `feat:` — новая возможность, `fix:` — исправление, `docs:` — README и руководства.

## Pull request

Заполните шаблон PR: назначение, затронутые скрипты, целевое окружение, выполненная ручная проверка, откат и безопасность, обновленная документация. Фрагменты вывода команд полезнее снимков экрана.

В `main` попадают только PR с зеленой проверкой `checks`, одобрения не требуются; слияние — rebase или squash, история линейная.

## CI и вклад из форка

Проверка `checks` (`.github/workflows/ci.yml`) выполняет первые три команды полной проверки (синтаксис, shellcheck, тесты) на self-hosted раннере владельца; пробелы в конце строк, ссылки и версии проверяют тесты внутри шага Tests. Репозиторий публичный, поэтому на этот раннер идут только push владельца и его PR из веток этого репозитория. У PR из форка задание `checks` попадает на hosted-раннер и падает на первом шаге, до checkout: недоверенный код не исполняется.

Это ожидаемо, а не ошибка вашего PR. Владелец переносит вклад в ветку репозитория, проверяет его там и сливает. Чтобы ускорить ревью, приложите вывод четырех команд полной проверки с вашей машины.

Выпуски (теги `vГГГГ.ММ.ДД` и GitHub Release) делает владелец; в PR их создавать не нужно.
