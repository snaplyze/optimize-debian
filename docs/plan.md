План — единый реестр задач и запись хода. Задачи и вехи трекера — его копия и вход для новых задач: у открытой задачи плана есть issue с ID в названии, вехой этапа и ссылкой на раздел задачи. Сначала обновляется план, затем трекер.

Очередь — единственное место статуса, зависимостей и номера issue. В разделе задачи — тип, приоритет с основанием, уверенность, доказательство, влияние (у дальних задач может входить в основание приоритета), решение (трудоемкость, риски), границы, результат, приемка и ход (решение, проверка, следующий шаг, выводы неудачных попыток; у BLOCKED — что и от кого разблокирует). Статусы: TODO, IN_PROGRESS, BLOCKED, DONE. Приоритеты: P0 — критично, P1 — высокий ущерб, P2 — обычное, P3 — низкий риск. Строки кода и документов указаны по `08cda50`.

### Задачи

#### BUG-1

**Мини-ПК: шаг ядра вызывает неопределенную функцию.** Дефект · P1 — путь по умолчанию на Debian 12 обрывается посреди настройки: шаг ядра включен по умолчанию (`INSTALL_KERNEL=true`, `optimize_mini_pc.sh:853`) · уверенность высокая: воспроизведено на Debian 12. Найдено ревью при упорядочивании плана 2026-10-20.

- Доказательство: `optimize_mini_pc.sh:1257` вызывает `run_apt_update_with_diagnostics` внутри `if $INSTALL_KERNEL` и `if [ "$distro_version" = "12" ]`; функция не определена ни в скрипте, ни в `lib/` (`grep` находит только вызов); скрипт работает под `set -e` (`:14`), поэтому код 127 завершает его.
- Влияние: на Debian 12 мини-ПК остается настроенным частично — после шагов пользователя и SSH, без Docker, Samba и остального.
- Решение: определить функцию в `optimize_mini_pc.sh` до защиты `OPTIMIZE_SOURCE_ONLY` (вариант VPS, `optimize_vps.sh:696`); объединение реализаций обновления индекса — в PERF-1. Трудоемкость S. Риск: низкий.
- Границы: `optimize_mini_pc.sh`, `tests/`.
- Результат: шаг ядра на Debian 12 не обрывается.
- Приемка: тест — после `OPTIMIZE_SOURCE_ONLY=1 source` копии `optimize_mini_pc.sh` без `lib/` функция `run_apt_update_with_diagnostics` определена, с моком `apt-get` при успехе возвращает 0, при сбое — ненулевой код и сообщение с контекстом; на одноразовой Debian 12 шаг ядра проходит без кода 127.
- Ход: выполнено — функция определена в `optimize_mini_pc.sh` рядом с `package_available`; тест `test_apt_update_diagnostics` (`tests/test_optimize_distro_support.sh`) проверяет копии VPS и мини-ПК без `lib/`: до правки FAIL, после PASS. Проверка на Debian 12 (контейнер `debian:12`, `sha256:bc49dc19…`, реальный `apt`): ветка Debian 12 шага ядра до правки завершилась кодом 127 (`run_apt_update_with_diagnostics: command not found`), после — кодом 0.

#### CI-1

**`main` без защиты и обязательных проверок.** Сборка и доставка · P2 — `main` и есть релиз (README и `docs/` запускают скрипты прямо из `main`), а слиянию с красной или не отчитавшейся проверкой ничто не мешает · уверенность высокая.

- Доказательство: `gh api repos/snaplyze/optimize-debian/branches/main/protection` → 404 «Branch not protected»; `…/rulesets` → `[]` (2026-10-20). Коммиты `main` приходят через PR по соглашению, а не по защите.
- Влияние: регрессия попадает к пользователям без проверки. Если сделать `checks` обязательной как есть, PR, для которого задание пропущено условием `if:` (не владелец), получит зеленый статус: по docs.github.com («Troubleshooting required status checks») пропущенное по условию задание отчитывается как «Success».
- Решение: ruleset для `main` — только через PR, обязательная `checks`, запрет force push и удаления ветки; обязательной сделать проверку, которая для недоверенного источника падает, а не пропускается. Трудоемкость S. Риск: ошибка в настройке заблокирует слияния владельца.
- Границы: настройки репозитория — только владелец; `.github/workflows/ci.yml` — агент, если для недоверенного источника нужна падающая проверка.
- Результат: в `main` нельзя попасть без PR и прошедшей `checks`.
- Приемка: `gh api` показывает правило с обязательной проверкой и запретом прямого push; PR с падающей проверкой слить нельзя.
- Ход: разблокирует владелец — решение и настройка защиты ветки и обязательных проверок; затем агент проверяет их через `gh api`.

#### ARCH-2

**Копии функций `lib/` без контроля расхождений.** Архитектура (дублирование) · P2 — у пользователей (`bash <(curl …)`) работают встроенные копии, а не `lib/`, и ничто не проверяет, что они совпадают · уверенность высокая.

- Доказательство: копии функций `lib/common.sh` и `lib/tui.sh` в четырех `optimize_*.sh` на `dc63a34` совпадают по поведению — сравнение нормализованного `declare -f`; различия только в стиле у `common_render_docker_debian_source`, `common_render_debian_backports_source`, `tui_prompt_yn`, `tui_radiolist`. Теста такого сравнения нет; AGENTS.md: «текст копий тесты не сравнивают».
- Влияние: исправление в `lib/` может не дойти до копии, и тесты `lib/` этого не заметят.
- Решение: тест — для каждой функции `lib/*.sh` сравнить нормализованный `declare -f` с копией в каждом `optimize_*.sh`, где она есть. С ним тесты `lib/` покрывают и копии. Генерация однофайловых скриптов из исходников вместо ручных копий — вариант L, меняет процесс; выбор за владельцем. Трудоемкость S. Риск: низкий.
- Границы: `tests/` (новый тест); код продукта не меняется.
- Результат: семантическое расхождение любой копии с `lib/` ломает тест.
- Приемка: тест PASS на текущем коде и FAIL при мутации любой копии (проверено мутацией).
- Ход: выполнено — `tests/test_embedded_copies.sh` подключает копию каждого `optimize_*.sh` без `lib/` и строго сравнивает `declare -f` каждой копии с `lib/` (61 копия в 4 скриптах, 0,12 с). Чтобы сравнение было строгим, четыре функции `lib/` (`common_render_docker_debian_source`, `common_render_debian_backports_source`, `tui_prompt_yn`, `tui_radiolist`) приведены к тексту копий, одинаковому во всех скриптах; поведение не менялось, тесты `lib/` PASS. Проверка: мутации копий `common_safe_write_sudoers` (мини-ПК), `tui_prompt_yn` (WSL2), `common_render_docker_debian_source` (amnezia) — FAIL с именем функции и diff. Прежний шаг 2 (перенос разошедшихся хелперов в `lib/`) вынесен: APT-хелперы — в ARCH-1, PERF-2, PERF-1, остальные — в ARCH-6.

#### SEC-3

**Запись sudoers не атомарна и удаляет прежний файл.** Безопасность, дефект · P2 — нарушен инвариант проекта «атомарная запись sudoers с проверкой до применения» (AGENTS.md, «Atomic Sudoers Validation»; README и `docs/` называют запись атомарной) · уверенность высокая.

- Доказательство: `lib/common.sh:156-179` — `printf > "$target_file"` прямо в `/etc/sudoers.d/…`, затем `chmod 440`, затем `visudo -cf`, при ошибке `rm -f "$target_file"`; код записи не проверяется; без `visudo` проверка молча пропускается. Копии во всех `optimize_*.sh` совпадают по поведению. Проверка на снимке: существующий валидный файл + невалидное содержимое → код 2, файла больше нет; файл, недоступный для записи, → код 0 со старым содержимым.
- Влияние: до проверки sudo читает непроверенный файл; при невалидном содержимом теряется и прежнее валидное правило; сбой записи выдается за успех.
- Решение: временный файл в том же каталоге с точкой в имени (sudo пропускает такие файлы в `#includedir`), `chmod 440`, `visudo -cf` на нем, затем `mv -f`; проверять код записи; отсутствие `visudo` — явная ошибка. Трудоемкость S. Риск: низкий; временный файл удалять при любом выходе.
- Границы: `lib/common.sh`, копии `common_safe_write_sudoers` в четырех `optimize_*.sh`, `tests/test_common_helpers.sh`.
- Результат: целевой файл меняется только на проверенное содержимое, одним `mv`.
- Приемка: тест — существующий валидный файл и невалидное содержимое → файл не изменился, код 2; валидное содержимое → новый текст и права 0440; сбой записи → ненулевой код; копии совпадают с `lib/` (тест ARCH-2).
- Ход: выполнено — `common_safe_write_sudoers` пишет во временный файл с точкой в имени в том же каталоге, ставит 0440, проверяет `visudo -cf` и только потом делает `mv -fT` (каталог на месте цели — ошибка); нет `visudo` или сбой записи — код 1, невалидное содержимое — код 2, временный файл удаляется во всех ветках. Копии в четырех скриптах совпадают с `lib/` (тест ARCH-2); сообщения вызывающих мест уточнены, amnezia при сбое останавливается с ошибкой. Проверка: `test_safe_write_sudoers` до правки FAIL, после PASS; мутации «без chmod 440», «временный файл остается», «временный файл без точки в имени», «`mv` без `-T`» — FAIL; независимое ревью — без блокирующих замечаний, три мелких исправлены; на Debian 12 от root (контейнер `debian:12`, настоящий `sudo`): версия из `main` при невалидном содержимом удаляла прежний `/etc/sudoers.d/ops` (пользователь терял sudo), новая сохраняет его, `sudo -l -U ops` — `NOPASSWD: ALL`.

#### SEC-4

**Мини-ПК: SSH закаляется без `sshd -t` и проверки входа.** Безопасность (потеря доступа) · P2 — можно потерять удаленный доступ; у мини-ПК обычно есть локальная консоль, поэтому не P1 · уверенность высокая.

- Доказательство: `optimize_mini_pc.sh:1205-1218` — сразу после вставки ключа пишется `/etc/ssh/sshd_config.d/99-hardening.conf` (`PermitRootLogin no`, `PasswordAuthentication no`, `AllowUsers $NEW_USER`) и выполняется `systemctl restart ssh … || true`. Нет `sshd -t`, сбой рестарта скрыт, строка не проверяется как публичный ключ, нет паузы «проверьте вход в другом окне», как в VPS (`optimize_vps.sh:1026-1032`). Amnezia проверяет `sshd -t` перед рестартом (`optimize_amnezia_host.sh:1174-1182`).
- Влияние: неверный ключ или ошибка конфигурации закрывают вход по SSH.
- Решение: проверка ключа (`ssh-keygen -l -f`), `sshd -t` перед рестартом с удалением drop-in при ошибке, видимая ошибка рестарта, пауза подтверждения входа. Трудоемкость S. Риск: низкий.
- Границы: `optimize_mini_pc.sh` (шаг SSH), `tests/`.
- Результат: hardening применяется только с рабочим ключом и валидной конфигурацией.
- Приемка: тест на моках `sshd` и `systemctl` — при падении `sshd -t` drop-in удален и рестарта нет; при невалидном ключе hardening не применяется.
- Ход: следующий шаг — вынести запись drop-in в функцию и покрыть тестом.

#### DATA-3

**Upgrade: при сбое `sshd -T` ожидается порт 22.** Данные (проверка сохранения доступа) · P2 — ложная остановка после уже выполненного шага обновления или ложный успех, если порт 22 занят другим процессом · уверенность высокая по коду.

- Доказательство: `upgrade-to-debian13.sh:369-372` — `sshd -T > … 2>/dev/null || true`, порты берутся из этого вывода, при пустом результате `SSH_EXPECTED_PORTS="22"`; их проверяет `ensure_ssh_is_healthy` (`:476-530`) после каждого шага.
- Влияние: на сервере с SSH не на 22 и сбоем `sshd -T` скрипт останавливается посреди обновления 11 → 12 → 13.
- Решение: при сбое `sshd -T` остановиться до изменений с объяснением, либо взять порты, которые слушает процесс sshd (`ss -tlnp`). Трудоемкость S. Риск: низкий.
- Границы: `upgrade-to-debian13.sh` (`snapshot_remote_access_state`), `tests/test_upgrade_to_debian13.sh`.

#### DATA-6

**Upgrade: официальный `.list` с опциями через пробел считается сторонним.** Данные · P3 — официальный источник уходит в отключенные вместо переноса как официальный; шаг переключения все равно пишет канонический `debian.sources`, поэтому обновление не ломается · уверенность высокая: проверено на коде `main`. Найдено при выполнении DATA-1 2026-10-21, вне зафиксированного объема.

- Доказательство: `is_official_debian_list_file` (`upgrade-to-debian13.sh`) берет URI как `$3`, если `$2` начинается с `[`; строка `deb [arch=amd64 signed-by=/usr/share/keyrings/debian-archive-keyring.gpg] http://deb.debian.org/debian bookworm main` разбивается на поля по пробелу внутри скобок, URI определяется неверно, файл считается сторонним (проверено вызовом функции на версии `9970b4b`); без пробела в скобках — официальным.
- Решение: пропускать все поле `[...]` целиком (до закрывающей `]`), затем брать URI. Трудоемкость S. Риск: низкий.
- Границы: `upgrade-to-debian13.sh` (`is_official_debian_list_file`), `tests/test_upgrade_to_debian13.sh`.
- Результат: опции в квадратных скобках не влияют на классификацию.
- Приемка: тест — `.list` с `[arch=amd64 signed-by=…]` и официальным URI признается официальным, с тем же набором опций и сторонним URI — сторонним.

#### BUG-3
