### Задачи

#### CI-1 — `main` без защиты и обязательных проверок

- Отметка: Аудит 2026-10-20. Тип: сборка и доставка. Приоритет: P2 — `main` и есть релиз (README и `docs/` запускают скрипты прямо из `main`), а слиянию с красной или не отчитавшейся проверкой ничто не мешает. Уверенность: высокая.
- Доказательство: `gh api repos/snaplyze/optimize-debian/branches/main/protection` → 404 «Branch not protected»; `…/rulesets` → `[]` (2026-10-20). Сейчас все коммиты `main` пришли через PR #2 и #4 — это соглашение, а не защита.
- Влияние: регрессия попадает к пользователям без проверки. Если сделать `checks` обязательной как есть, PR, для которого задание пропущено условием `if:` (не владелец), получит зеленый статус: по docs.github.com («Troubleshooting required status checks») пропущенное по условию задание отчитывается как «Success».
- Решение: ruleset для `main` — изменения только через PR, обязательная проверка `checks`, запрет force push и удаления ветки. Чтобы пропуск по `if:` не давал зеленого статуса, обязательной сделать проверку, которая для недоверенного источника падает, а не пропускается. Трудоемкость S. Риск: ошибка в настройке заблокирует слияния владельца. Настройки репозитория меняет только владелец.
- Результат: в `main` нельзя попасть без PR и прошедшей `checks`.
- Зависимости: нет.
- Приемка: `gh api` показывает правило с обязательной проверкой и запретом прямого push; PR с падающей проверкой слить нельзя.
- Трекер: [#6](https://github.com/snaplyze/optimize-debian/issues/6)
- Текущая запись: BLOCKED — нужны решение и настройка владельца (защита ветки и обязательные проверки). Следующий шаг: владелец включает ruleset; агент проверяет его через `gh api`.

#### SEC-3 — Запись sudoers не атомарна и удаляет прежний файл

- Отметка: Аудит 2026-10-20. Тип: безопасность, дефект. Приоритет: P2 — нарушен инвариант проекта «атомарная запись sudoers с проверкой до применения» (AGENTS.md, «Atomic Sudoers Validation»; README и `docs/` называют запись атомарной). Уверенность: высокая.
- Доказательство: `lib/common.sh:156-179` — `printf > "$target_file"` прямо в `/etc/sudoers.d/…`, затем `chmod 440`, затем `visudo -cf`, при ошибке `rm -f "$target_file"`; код записи не проверяется; без `visudo` проверка молча пропускается. Встроенные копии во всех `optimize_*.sh` совпадают по поведению. Проверка на снимке: существующий валидный файл + невалидное содержимое → код 2, файла больше нет; файл, недоступный для записи, → код 0 со старым содержимым.
- Влияние: до проверки sudo читает непроверенный файл; при невалидном содержимом теряется и прежнее валидное правило; сбой записи выдается за успех.
- Решение: временный файл в том же каталоге с точкой в имени (sudo пропускает такие файлы в `#includedir`), `chmod 440`, `visudo -cf` на нем, затем `mv -f`; проверять код записи; отсутствие `visudo` — явная ошибка. Изменить `lib/common.sh` и копии в четырех `optimize_*.sh`. Трудоемкость S. Риск: низкий; временный файл удалять при любом выходе.
- Результат: целевой файл меняется только на проверенное содержимое, одним `mv`.
- Зависимости: нет.
- Приемка: тест — существующий валидный файл и невалидное содержимое → файл не изменился, код 2; валидное содержимое → новый текст и права 0440; сбой записи → ненулевой код. Тест исполняется и для встроенных копий (см. TEST-1).
- Трекер: [#7](https://github.com/snaplyze/optimize-debian/issues/7)
- Текущая запись: TODO. Следующий шаг: тест на существующий файл (сейчас падает), затем правка `lib/` и копий.

#### SEC-4 — Мини-ПК: SSH закаляется без `sshd -t` и проверки входа

- Отметка: Аудит 2026-10-20. Тип: безопасность (потеря доступа). Приоритет: P2 — можно потерять удаленный доступ; у мини-ПК обычно есть локальная консоль, поэтому не P1. Уверенность: высокая.
- Доказательство: `optimize_mini_pc.sh:1205-1218` — сразу после вставки ключа пишется `/etc/ssh/sshd_config.d/99-hardening.conf` (`PermitRootLogin no`, `PasswordAuthentication no`, `AllowUsers $NEW_USER`) и выполняется `systemctl restart ssh … || true`. Нет `sshd -t`, сбой рестарта скрыт, введенная строка не проверяется как публичный ключ, нет паузы «проверьте вход в другом окне», которая есть в VPS (`optimize_vps.sh:1026-1032`). Для сравнения: amnezia проверяет `sshd -t` перед рестартом (`optimize_amnezia_host.sh:1174-1182`).
- Влияние: неверный ключ или ошибка конфигурации закрывают вход по SSH.
- Решение: проверка ключа (`ssh-keygen -l -f`), `sshd -t` перед рестартом с удалением drop-in при ошибке, видимая ошибка рестарта, пауза подтверждения входа. Трудоемкость S. Риск: низкий.
- Результат: hardening применяется только с рабочим ключом и валидной конфигурацией.
- Зависимости: нет.
- Приемка: тест на моках `sshd` и `systemctl` — при падении `sshd -t` drop-in удален и рестарта нет; при невалидном ключе hardening не применяется.
- Трекер: [#8](https://github.com/snaplyze/optimize-debian/issues/8)

#### ARCH-2 — Ручные копии общих функций без контроля расхождений

- Отметка: Аудит 2026-10-20. Тип: архитектура (дублирование). Приоритет: P2 — у пользователей работают копии, а не `lib/`, и копии вне `lib/` уже разошлись по поведению. Уверенность: высокая.
- Доказательство: копии функций из `lib/common.sh` и `lib/tui.sh` в четырех `optimize_*.sh` сейчас совпадают по поведению — сравнение нормализованного `declare -f` на снимке, различия только в стиле у `common_render_docker_debian_source`, `common_render_debian_backports_source`, `tui_prompt_yn`, `tui_radiolist`; тест такого сравнения нет. Функции вне `lib/` разошлись: `safe_install` (ARCH-1, PERF-1), `package_available`, `wait_for_dpkg_lock` (PERF-2), `enrich_apt_components` (мини-ПК без проверки `mktemp`, `optimize_mini_pc.sh:618`; WSL2 обрабатывает только строки `deb`, `optimize_wsl2.sh:1104`), `ensure_time_sync_service` и `system_clock_synchronized` (разные контракты кода возврата и свойства `timedatectl`: `optimize_amnezia_host.sh:362,395`, `optimize_vps.sh:721,763`), `run_apt_update_with_diagnostics`.
- Влияние: исправление в одном скрипте не доходит до остальных; поведение одинаковых шагов различается между профилями.
- Решение: (1) тест эквивалентности — для каждой функции `lib/*.sh` сравнить нормализованный `declare -f` с копией в каждом скрипте (S); (2) перенести общие APT- и time-sync-хелперы в `lib/` с одной реализацией и копиями под тем же тестом (M). #### PERF-2 — Ожидание блокировки dpkg зависит от `fuser`

- Отметка: Аудит 2026-10-20. Тип: производительность и надежность. Приоритет: P2 — без `fuser` ожидание не работает, и `apt-get` падает, если блокировку держит другой процесс. Уверенность: средняя — наличие `fuser` в облачных образах не проверено (Г-5).

Для `apt-get update` опция блокировку списков не покрывает — нужен ограниченный повтор. Трудоемкость S–M. Риск: низкий.
- Результат: установка ждет освобождения блокировки без внешних утилит.
- Зависимости: ARCH-2 (общий APT-хелпер).
- Приемка: тест с `PATH` без `fuser` и моком `apt-get`, который сначала сообщает о занятой блокировке, — установка дожидается и завершается; на одноразовой Debian — прогон при запущенном `apt-get`.
